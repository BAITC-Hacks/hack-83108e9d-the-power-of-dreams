## Отказ однократной загрузки каталога

Зафиксировать в design точный тип ожидаемой ошибки loader и состояние composition: `ready(snapshot)` либо `unavailable(safe category)`. Composition выполняет одну общую попытку загрузки на процесс и сохраняет её результат, включая ожидаемый отказ; параллельные первые запросы используют ту же попытку. Вне контролируемой границы не должно оставаться выброшенной ошибки/отклонённого promise ожидаемого CSV-сбоя при импорте route-модуля.

При отсутствующем, нечитаемом или невалидном CSV HTTP-сервер остаётся доступным: GET options и синтаксически корректный POST recommendations получают HTTP 503 с `CATALOG_UNAVAILABLE` и новым `requestId` для каждого запроса. Сохраняется безопасная категория ошибки, не готовый HTTP-ответ с прежним requestId и не содержимое файла. AI не вызывается. Повторные запросы не перечитывают файл и не запускают скрытые retries; после исправления CSV нужен restart. Неожиданную программную ошибку нельзя переклассифицировать как обычную недоступность каталога.

P02 отвечает за явный typed failure loader; P05 — за сохранение состояния и формат HTTP. В проверках P05 запуск с отсутствующим/повреждённым CSV должен привести к достижимым 503 обоих endpoints, без AI; повторный запрос сохраняет отказ без новой загрузки, исправление файла и restart восстанавливают нормальный путь. Это проектное решение для переноса в OpenSpec, не свидетельство текущей реализации.

## Минимальная live-проверка AI

Зафиксировать один проходной набор, связанный с [архитектурными сценариями](../architecture/implementation-and-verification.md#data-derived-rehearsal-cases):

- Dense: Алматы / Ведущий / корпоратив / `2026-10-10` / `1500000` KZT; карточки `HK-88430`, `HK-29829`, `HK-27222`.
- Rare: Алматы / Флорист / свадьба / `2026-10-10` / `500000` KZT; карточка `HK-39372`.

Язык/длительность не заданы. Минимум — реальные AI-ответы для всех четырёх карточек этих двух запросов. Для каждой координатор фиксирует `pass`, `fail` или `not_run` и краткое основание по каждому применимому критерию:

1. Принятая цитата буквально соответствует описанию своего ID и проходит ограничения evidence; fallback не считается успешной live-цитатой.
2. Цитата содержит предметный стиль/специализацию, релевантные заданному формату, без выдуманных пожеланий, общих похвал или списка клиентов вместо обоснования. Записать, **какой именно факт** связывает профиль с запросом; «релевантно» без объяснения недостаточно.
3. В готовом тексте факты/числа соответствуют запросу и structured fields; нет неподтверждённых качества, цены, доступности или возможностей; длина — 1–2 предложения.
4. Для dense — при скрытых именах все три объяснения отличаются предметным содержанием и не взаимозаменяемы. Отличие одной цены или имени недостаточно. Для rare парное сравнение неприменимо; остальные критерии обязательны.

В evidence-таблице OpenSpec записать normalized request, ID карточки, статусы и причины, модель, dataset revision/hash, проверенный source SHA, дату/проверяющего и общее решение по набору. Не сохранять ключи, полный prompt/provider payload или полные описания. Весь набор проходит только при `pass` всех применимых критериев для четырёх карточек; непроверенное явно остаётся `not_run`. Literal matching само по себе не закрывает качество.

P01 выполняет предварительную dense-проверку и проверку готового сквозного текста. P04 закрывает source/relevance/distinctiveness для dense + rare; окончательный текст renderer и весь набор подтверждает P07. Существующее достаточное evidence повторно использовать, если код/prompt/модель/данные/рендеринг не изменились. Живые ответы итоговых трёх timing-запросов могут одновременно служить этим набором (например, dense, rare, dense); отдельную дублирующую серию не требовать. При `fail` — конкретный дефект и ограниченное исправление prompt/renderer с повтором затронутого случая; не выбирать молча лучший результат из повторных вызовов. Корректный fallback проходит проверку устойчивости, но не этот live-критерий.

## Приёмка и handoff

- OpenSpec strict-validation пройдена; каждому требованию соответствует наблюдаемый сценарий, каждому заданию — владелец файлов и зависимости.
- DTO покрывают три исхода и четыре explanation mode, материализованные примеры используют их без противоречий. Типы не зависят от UI/провайдеров/хранилища.
- В OpenSpec зафиксированы политика сохранения отказа каталога, проходной live-набор и таблица оценки, условия промежуточной передачи и бюджет с резервом P07. Эти плановые решения не отмечаются как уже пройденные execution checks.
- Установленные инструменты и закреплённые зависимости доступны в подготовленной базе; product build пока не объявляется пройденным, если приложения ещё нет.
- Проверены фактические пути, base SHA, remote, harness и запреты. В OpenSpec записаны точный SHA базы, источник действующих ограничений и готовность P01. Значения не выдумывать.
- Возврат: contracts/example paths + commit; base/harness revision; список принятой существующей подготовки; нерешённые holds. Нет committed base — нет заявления о готовности независимых worktree.
